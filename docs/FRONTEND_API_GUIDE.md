# Progress, Account, Dietary, and Integration APIs

All URLs below are relative to `http://127.0.0.1:8000/api/v1`. All require
`Authorization: Bearer {{access_token}}`. JSON requests use `Content-Type: application/json`.
Errors retain `{"error":{"code":"...","message":"...","details":{}}}`.

## Weight History

| Method | Route | Request | Response |
| --- | --- | --- | --- |
| PUT | `/weight-logs/{log_date}` | `{"weight_kg":80}` | 200, saved record |
| GET | `/weight-logs` | Optional `start_date`, `end_date`, `limit`, `offset` | 200, history and progress |
| DELETE | `/weight-logs/{log_date}` | None | 204, or `WEIGHT_LOG_NOT_FOUND` |

Dates are ISO calendar dates, such as `2026-10-20`. PUT creates or replaces the user's
record for that date atomically; repeated writes cannot create duplicates. Weight is
20-500 kg, finite. Dates up to one calendar day ahead of UTC today are allowed to accommodate
local "today" in UTC+ timezones; later dates return `FUTURE_LOG_DATE`. History is newest first,
defaults to 100 rows, and accepts `limit=1..365`, `offset>=0`.

Example saved record (UUID/timestamps are generated by the server):

```json
{"id":"<uuid>","log_date":"2026-10-20","weight_kg":80,"created_at":"<UTC timestamp>","updated_at":"<UTC timestamp>"}
```

With earliest recorded weight 85, latest 80, and profile `target_weight_kg=75`:

```json
{
  "items": [],
  "total": 2,
  "limit": 100,
  "offset": 0,
  "progress": {
    "starting_weight_kg": 85,
    "current_weight_kg": 80,
    "target_weight_kg": 75,
    "change_kg": -5,
    "remaining_kg": 5,
    "progress_percent": 50
  }
}
```

The example omits item details for brevity. Progress always uses the entire user's history,
independently of pagination/date filters. It supports gain/loss, clamps progress to 0-100%,
and reports zero remaining once the target is passed in the intended direction. Without
measurements or a target, unavailable values are null. An initial measurement equal to
the target yields 100% only while the latest measurement equals the target. Logging never
updates `profile.weight_kg` or historical nutrition targets automatically.

## Manual Steps

| Method | Route | Request | Response |
| --- | --- | --- | --- |
| PUT | `/steps/{log_date}` | `{"steps":8500}` | 200, saved record with `source="manual"` |
| GET | `/steps` | Optional `start_date`, `end_date`, `limit`, `offset` | 200, `{items,total,limit,offset}` |
| GET | `/steps/{log_date}` | None | 200, or `STEP_LOG_NOT_FOUND` |
| DELETE | `/steps/{log_date}` | None | 204, or `STEP_LOG_NOT_FOUND` |

PUT replaces the total for the date; it does not increment it. Steps are strict integers
0-200000. Zero is a real recorded value; missing dates have no record. History and date rules
match weight logs. No calories burned, steps target, or wearable sync is inferred.

## Daily Metrics and Nutrition Summary

The subsequent nutrition/tracking batch adds `PUT/GET/DELETE /daily-metrics/{log_date}`
and `GET /daily-metrics?from=YYYY-MM-DD&to=YYYY-MM-DD`. PUT requires all three fields:
`{"water_glasses":8,"fruit_veg_servings":5,"sleep_hours":7.5}`. History returns the
usual `{items,total,limit,offset}` shape. Dates use the existing UTC+1-day write tolerance.
The records are user-owned and included in account export/deletion.

`GET /nutrition/intake` adds nullable `fiber_g` and `added_sugar_g`. `GET /insights`
adds structured `nutrition_summary` without removing generic `items`. Do not calculate
replacement scores in the frontend. See [Nutrition and Daily Tracking](NUTRITION_TRACKING.md)
for exact fields, full requests/responses, transparent product-score formulas, null
semantics for custom/legacy logs, and logging/nutrient completeness requirements.

## Daily Habits

| Method | Route | Request | Response |
| --- | --- | --- | --- |
| POST | `/habits` | `{"name":"Evening walk","description":null,"start_date":"2026-10-01"}` | 201, habit |
| GET | `/habits?date=2026-10-20` | Optional `date`, `limit=1..100`, `offset>=0` | 200, daily statuses |
| PATCH | `/habits/{habit_id}` | `{"name":"Morning walk","active":true}` | 200, updated habit |
| PUT | `/habits/{habit_id}/completions/{log_date}` | `{"completed":true}` | 200, `{date,completed}` |
| GET | `/habits/{habit_id}/history` | Optional `start_date`, `end_date` | 200, `{habit_id,items:[{date,completed}]}` |
| DELETE | `/habits/{habit_id}` | None | 204, deletes habit and completions |

Habits currently repeat daily. Names are trimmed, nonblank, and at most 150 characters;
description is nullable, at most 1000 characters. `start_date` defaults to UTC today and
allows the same one-calendar-day grace period. Daily statuses include `scheduled` and `completed`; dates before
the start are not scheduled. PATCH may clear `description` with null, but `name` and
`active` cannot be null. `active=false` preserves existing history and blocks new completions.
`completed=false` removes a completion idempotently; true inserts it idempotently.
Completions before start or more than one day after UTC today are rejected. History defaults to the last
30 days, allows at most 366 days, and excludes dates before the habit started.
There is no inferred historical schedule or custom frequency yet.

## Achievements and Insights

`GET /achievements` returns `{"items":[...]}`. Each item has `code`, `name`, `current`,
`target`, `unit`, and `unlocked`. Policy thresholds are explicit, with real counters:

| Code | Current Evidence | Target |
| --- | --- | --- |
| `first_weight` | Count of owned weight records | 1 |
| `weight_checkins_7` | Count of owned weight records | 7 |
| `steps_10000` | Maximum recorded daily steps | 10000 |
| `habit_completions_7` | Count of owned habit completions | 7 |
| `nutrition_days_7` | Distinct dates with active meal logs or standalone snacks | 7 |
| `first_recipe_completed` | Completed recipe execution sessions | 1 |

These are dynamic counters, not fabricated percentages or permanent awards. Editing/deleting
source records can change progress. Seven check-ins/days/completions need not be consecutive.

`GET /insights?start_date=2026-10-01&end_date=2026-10-20` returns:

```json
{
  "start_date":"2026-10-01",
  "end_date":"2026-10-20",
  "logged_nutrition_days":1,
  "items":[{
    "code":"recorded_nutrition",
    "message":"Average intake on days with recorded meals or snacks; partial days may be included.",
    "values":{"logged_days":1,"average_calories":300,"average_protein_g":20}
  }]
}
```

This sample assumes one logged day with 300 kcal and 20 g protein. Results use existing
meal nutrient snapshots plus standalone snack records. Missing days are not counted as
zero-intake days. Optional insights report manual steps, first-to-last weight change
(at least two measurements), and habit completions. No targets, weight, calories burned,
clinical/medical scores, diagnoses, or AI nutrition values are inferred. The additional
nonclinical nutrition summary is explicitly calculated as documented above. Empty periods return
`nutrition_data_missing`. Dates default to the last 30 days; maximum range is 366 days,
and end date must be no later than UTC today plus one calendar day.

## Notification Inbox

| Method | Route | Request | Response |
| --- | --- | --- | --- |
| POST | `/notifications/sync` | None | 200, `{"created_count":1}` |
| GET | `/notifications` | Optional `unread_only`, `limit=1..100`, `offset>=0` | 200, `{items,total,unread_count,limit,offset}` |
| PATCH | `/notifications/{notification_id}/read` | None | 200, notification |

Sync creates one notification per currently earned achievement, deduplicated by user/event
key. Call sync after tracking changes or when opening the inbox. GET performs no writes.
Notifications have `id`, `kind`, `title`, `message`, `read`, `read_at`, `created_at`.
Mark-read is idempotent; `read_at` stays stable on repeated calls. Unread count covers
the entire user's inbox, independently of pagination. Records snapshot the event at sync
time and remain historical if tracking data later changes. There is no push delivery,
reminder scheduler, or arbitrary client-controlled notification creation.

## Account Management

`POST /auth/change-password`:

```json
{"current_password":"StrongPassword123","new_password":"AnotherStrongPassword456"}
```

Returns 200 `{"message":"Password changed. Sign in again."}`. New passwords use the same
8-128 character policy and Argon2 hashing as existing auth. Incorrect current password:
400 `CURRENT_PASSWORD_INCORRECT`; unchanged password: 422 `PASSWORD_UNCHANGED`.
Successful change and existing password-reset both increment `token_version`, revoking
previous access/refresh tokens. The client must clear tokens and sign in again. Existing
version-zero tokens remain valid until their normal expiry or a password change/reset.

`DELETE /users/me` returns 204. It hard-deletes only the authenticated account and uses
database cascades for profile/preferences, plans, weeks, grocery lists, logs, execution
sessions, habits, notifications, weights, and steps. Tokens cannot authenticate afterward.
The shared food/recipe catalog is retained; recipes currently have no user ownership column.

`GET /users/me/export` returns 200 JSON with `schema_version`, `exported_at`, sanitized `user`,
and a `records` map keyed by table name. `Content-Disposition: attachment; filename="kcalm-data.json"`
and `Cache-Control: no-store` are set. Export includes all owned records and child snapshots,
including archived plans/lists. Credentials, token versions, provider secrets, and shared
catalog rows are excluded. This synchronous export is for MVP-sized histories; background
streaming export and retention policy remain business decisions.

## Dietary and Allergen Filtering

Save `dietary_restrictions=["pescatarian","halal"]` and canonical `allergies` in the existing
profile endpoints. Author recipes with explicit tags through existing recipe CRUD. Each
restriction requires its corresponding recipe tag, including both when both are selected.
Tags express catalog assertions; the backend does not infer halal certification or diet
membership from names or vegetarian/vegan tags. Catalog review/certification remains an
operator responsibility.

Allergies filter reviewed ingredient metadata throughout candidate preview, daily solver,
plan persistence, swaps, weekly plans, and adaptive planning because all reuse the same
candidate service. Existing AI allergy/safety language remains unsupported; AI cannot
author allergen metadata or guarantee safety.

Canonical codes: `peanut`, `tree_nut`, `milk`, `egg`, `fish`, `shellfish`, `soy`, `wheat`, `sesame`.
Aliases include peanuts, tree nuts, dairy, eggs, and soya; ambiguous nuts excludes both
peanuts and tree nuts. Gluten is not treated as wheat alone. Unknown allergy names produce
`unsupported_allergy` and no eligible recipes. Unknown or unreviewed ingredient metadata
produces `allergy_metadata_missing`; known overlap produces `allergy_conflict`.

Food metadata is nullable: null means unknown; reviewed `[]` means no listed allergens
according to the supplied reference. Both `allergen_codes` and a nonblank `allergen_reference`
are required for eligibility when the profile has supported allergies. No metadata is
guessed or automatically backfilled from food names, development fixtures, or USDA nutrients.
Use the operator-only command with an actual reviewed source:

```bash
python -m app.scripts.review_food_allergens --food-id <uuid> --allergens milk --reference '<reviewed source>'
```

Use `--allergens` with no codes only after review establishes the empty list. No public
endpoint lets clients declare foods allergen-free. Preview responses add `unsupported_allergies`,
`allergy_filtering_scope="reviewed_ingredient_metadata_only"`, and
`allergy_limitation="Cross-contact and medical safety are not assessed."`.
`allergy_filtering_supported` describes supported profile codes, not a safety certificate.
Without reviewed catalog data, allergy-constrained generation can be infeasible; this is intentional.

## Grocery Additions

Existing endpoints and editing behavior are retained. Grocery detail responses additionally
return `item_count`, `checked_item_count`, and `completion_percent` derived from current
items. An empty list reports 0%. Categories remain the existing grocery categories;
store-specific aisles, prices, stock, and delivery are not fabricated.

## Integration Capabilities

`GET /integrations` returns `{items:[...]}`; `GET /integrations/{code}` returns one record.
Each has `code`, `name`, `capabilities`, `status`, and `connection_verified=false`.
Unknown codes return `INTEGRATION_NOT_FOUND`.

Implemented entries reference the existing providers: `usda` (search/import), `openai`
(language constraints), `smtp` (reset email). Status is `configured` or `not_configured`
based on necessary deployment settings, never on a simulated connection. No credentials
are returned and no provider call is made by these endpoints. Existing provider routes
report their real upstream failures when invoked.

`wearable_sync`, `grocery_delivery`, and `push_notifications` report `not_implemented`.
Provider selection, OAuth/app registration, scopes/consent, secure credential storage,
webhook verification, retry policy, and credentials are required before those can connect.
The typed `app/integrations/registry.py` catalog is the extension point; actual provider
clients continue to live under `app/integrations`, with workflows under services.
